# Rain Explorer integration boundary

Rain Explorer will reference only `RainArchives.Contracts` and `RainArchives.Client`. It will host a Rain-specific adapter that translates archive DTOs into Rain’s location, tab, preview, drag/drop, and activity concepts. Rain Archives never references Rain Explorer, its WPF controls, view models, navigation services, or operation classes.

## Location identity and navigation

- A root open location is `(archive source identity, archive fingerprint, internal normalized path, duplicate ordinal where required)`. A nested location adds an ordered chain of `(parent archive fingerprint, persistent source-entry path, duplicate ordinal, child archive fingerprint)` segments. A session `EntryId` is an efficient ephemeral key, not persistent history data. Protocol 1.3 exposes the persistent path/ordinal only when `IArchiveClient.SupportsFeature("persistent-entry-keys")` is true; Rain must not infer or persist those fields from an older negotiated peer.
- A tab owns or leases one archive session. Child navigation reuses that session while its fingerprint remains valid. Back/forward history stores the persistent tuple and resolves fresh entry IDs after reopen.
- Breadcrumb segments carry display text plus the persistent internal path/ordinal. They do not use extracted filesystem paths.
- If the source identity/fingerprint changes, the client reports invalidation. Rain marks the tab stale and offers an explicit reopen; it does not silently continue with old IDs or mix old/new metadata.

## Listing and search

- Paged listing returns provider-neutral entry descriptors and safety annotations. Exact per-open capabilities and protocol-1.4 volume-set identity come from the opened `ArchiveDescriptor`, not from each `ListEntriesResponse` row. The Rain adapter maps both surfaces to its item model without losing duplicate entries. Confirmed multipart sessions currently advertise listing and volume-reading (plus encrypted reading where applicable), but not entry streaming, integrity testing, or extraction. Unknown volume sets are also list-only and do not claim volume-reading. Every Rain command and affordance must bind to the current opened descriptor rather than a format-wide assumption.
- Protocol 1.22 exposes paged listing but no search request. The first Rain Explorer integration therefore performs bounded filename search over its validated Rain-owned in-memory descriptor index and returns locally projected parent/breadcrumb state. A future Worker-side indexed search would require an additive contract. Content search is a separate opt-in operation with decoded-byte/nesting limits; it is never triggered merely by typing a filename query.

## Preview streams and cache ownership

- Protocol 1.5 supplies a complete-entry stream lease with session/entry ID, maximum decoded bytes, optional password slot, exact worker authentication, bounded frames, and acknowledged cancellation. Range/seek requests are intentionally deferred; the current API rejects a declared entry larger than the requested ceiling instead of returning an ambiguous truncated preview. Raw entry streams are not called “integrity tested.”
- Preview affordances bind to the opened descriptor's `OpenEntryStream` capability. In current source this includes the checked managed ZIP/7z/non-solid-RAR/TAR/compression-stream variants, while solid RAR remains test/extract-only and carries `archive.preview_unavailable`; Rain Explorer must explain or disable preview for that session and must not synthesize an unbounded sequential fallback.
- `ArchiveEntryStreamLease` owns the data pipe and exposes a read-only non-seekable stream. Rain’s preview subsystem owns that lease lifetime and must dispose it on tab/preview replacement; archive/client close also settles owned leases.
- Current `RainArchives.Client.ArchivePreviewCache` is the bounded bridge for seek-only in-process previewers. Rain precreates an app-private non-reparse directory, then the cache materializes the complete authenticated lease into a random `CreateNew`/delete-on-close file held with `FileShare.None`. Default admission is 512 MiB across at most eight active leases. It returns only an `ArchivePreviewLease` containing session/entry identity, exact length, and a read-only seekable wrapper over that same exclusive handle after terminal completion and length validation; it does not expose or reopen the file path. Closing the wrapper, lease, cache, tab-owned preview, or client-owned preview policy must release it.
- `RainArchives.App` now demonstrates one presentation policy over that cache: strict text only, a 1 MiB display ceiling plus one detection byte, visible Unicode/control escaping, and one active plus one newest pending request. Those limits and WPF state are App policy, not DTOs or a requirement that Rain Explorer adopt the same visual presenter. Rain Explorer may build its own bounded previewers, but each must retain the stream/cache security invariants and must not infer active-content safety from a filename extension.
- The current cache is not a Shell-preview or execution handoff and makes no download-provenance propagation claim. A future external path lease needs explicit provenance application, private-directory ownership, lifetime acknowledgement, and cleanup semantics before use. Secrets, entry contents, source paths, and private cache paths do not enter ordinary activity logs.

## Explicit nested navigation

- Protocol 1.6 exposes `OpenNestedArchiveAsync` only when `nested-archive-open` was negotiated. Rain offers it as an explicit Open as archive action for one selected material file; ordinary listing, filename search, preview, breadcrumb construction, and tab restore never decode nested payloads speculatively.
- The response supplies a child descriptor, parent session ID, source entry ID, depth, exact materialized bytes, and ancestry-chain bytes. Rain represents the child as another archive root in the same tab or a new tab according to user action, then stores the persistent source-entry chain above for history. Reopen resolves fresh session/entry IDs one level at a time and stops honestly at the first changed, missing, password-locked, or newly unsupported level.
- The worker owns the immutable materialized source; Rain never sees its path. The client owns the relationship graph and closes known descendants deepest-first when their parent closes. A tab/cache must release its child session on navigation replacement or close, while a raw child session opened by another client remains that client's responsibility.
- Nested opening inherits the outer source's download provenance and uses the provider integrity-copy path, not the raw preview stream. Current limits are three explicit levels, 64 MiB default and 256 MiB hard per request, 256 MiB per ancestry chain, and 512 MiB across active/in-flight nested sessions. Rain may request a lower ceiling, but may not hide or retry a limit refusal with a larger value without a new user action.
- Confirmed multipart, unknown-volume, non-file, and unsupported solid-source cases remain disabled with the worker's structured reason. Solid RAR currently returns `nested.solid_source_deferred`; Rain must not work around that by extracting preceding members or recursively opening a temporary copy itself.

## New-archive creation

- Current protocol 1.24 negotiates `creation-expanded-tree-budget-v1`: `IArchiveClient.MaximumCreationTreeEntries` is 65,536 only when supported, otherwise 4,096. Explorer tracks it separately from explicit/root and legacy capability limits. Typed resource-limit diagnostics retain entry/byte/metadata/path/output reasons without provider text or automatic retry. The bounded creation dialog displays the current budget and follows the selected theme; [current repair evidence](creation-ui-remediation.md) supersedes older tree-count descriptions below.

- Protocol 1.7 exposes `StartZipCreationAsync` only when `zip-create-v1` was negotiated. This request is independent of an opened archive session: it carries one nonexistent destination path, zero to 4,096 explicit regular source-file/archive-path mappings totaling at most 64 GiB, and `Store`, `Fast`, `Balanced`, or `Maximum`. Its DTO remains unchanged under protocol 1.8.
- Protocol 1.8 separately exposes `StartZipTreeCreationAsync` only when `zip-create-directories-v1` was negotiated. It may combine explicit file mappings with at least one source-directory/archive-root mapping. Rain sends only the selected semantic roots; the worker expands them without following reparses, includes each root and empty descendant directory, and enforces one global 4,096-entry and 64-GiB regular-file-byte budget.
- Protocols 1.12-1.16 add complete-copy ZIP rebuild and typed ZIP write capabilities without changing the earlier creation requests. Rain may offer add/replace/delete, retained-file rename, bounded source-folder/tree edits, and explicit ZIP-representable metadata only for an eligible opened single-volume unencrypted ZIP whose current capability response advertises that exact operation. The output is a distinct absent ZIP, the original remains byte-identical, and no capability authorizes overwrite, replacement, in-place mutation, encryption, or split output.
- Protocol 1.17 adds distinct Store-only TAR explicit/tree creation and TAR capabilities. Protocol 1.18 adds distinct TAR.GZ/TAR.BZ2 explicit/tree requests, exact-one-source raw GZIP/BZIP2 requests, and managed-format capability discovery. Rain must build format/preset/source affordances from that typed response: TAR-family uses the bounded explicit/tree policy, while raw formats accept exactly one ordinary file and derive the synthetic member name from the destination stem. All responses keep rebuild, encryption, filename encryption, split, existing-destination replacement, and in-place update false unless a future additive contract proves otherwise.
- Protocol 1.23 adds a separate conditional RAR5 explicit/tree/capability surface. Rain Explorer shows RAR in the creation picker only as enabled when the connected Worker reports `Available`; `NotInstalled`, `UpdateRequired`, `UntrustedBinary`, `UnsupportedPlatform`, and `RestartRequired` remain visible fixed disabled reasons. Availability requires the user's separately installed, licensed, signed x64 WinRAR 7.23-through-7.x encoder at `C:\Program Files\WinRAR\Rar.exe`. Rain never bundles or discovers that executable through `PATH`, current directory, or registry, and protocol 1.22 peers negotiate no RAR creation feature.
- Protocol 1.9 separately exposes path-free `ListArchiveCreationRecoveriesAsync` and explicit `InspectArchiveCreationRecoveryAsync` only when `archive-creation-recovery-inspection-v1` was negotiated. Destination paths appear only after the user explicitly inspects one record, and inspection itself grants no cleanup, retry, or disposition authority. Protocol 1.10 adds `ApplyArchiveCreationRecoveryDispositionAsync` behind `archive-creation-recovery-disposition-v1`. Rain Explorer must present the freshly inspected assessment and only the applicable closed choices, require explicit confirmation, and send the exact inspected phase, sequence, and UTC journal timestamp with the selected action. A stale or conflicting response returns to inspection rather than guessing or retrying another action. The response is transport-neutral (`Completed` or `AlreadyCompleted`, action, final assessment, and resolution time); no WPF type crosses the boundary. The standalone App now demonstrates this read-first/exact-revision behavior, but its dialog and view models are not shared integration contracts and Rain Explorer must not reference them. The client owns cancellation containment and may terminate its own worker if synchronous destination I/O does not settle.
- Protocol 1.11 separately exposes `ListNestedWorkspaceRecoveriesAsync`, `InspectNestedWorkspaceRecoveryAsync`, and `DiscardNestedWorkspaceRecoveryAsync` behind `nested-workspace-recovery-v1`. Rain Explorer must show only the path-free opaque ID/count/byte/time evidence, request a fresh inspection before enabling discard, require explicit confirmation, and send the exact revision, source count, and total bytes unchanged. Protocol 1.21 adds `ReopenNestedWorkspaceRecoveryAsync` behind `nested-workspace-independent-reopen-v1`: it repeats that fresh workspace evidence plus one exact source ID/length, copies and redetects the source, and returns a new independent depth-zero root with zero chain bytes. It does not reconstruct the former parent chain, expose/adopt the temporary path, mutate the recovery workspace, or grant discard authority. Any refresh, failure, cancellation, changed assessment, or malformed response clears action authority; Rain never guesses a temporary path, retries automatically, or treats discard/reopen as equivalent. The current CLI and standalone App Recovery Center are proof review surfaces; Rain Explorer integration remains later work, and its provider must consume only the UI-neutral DTOs/client methods without referencing App, Worker, Core, providers, or Security.
- Rain Explorer routes **Create archive...** into the existing operation/activity system and observes the returned operation ID plus ordered progress/warning/terminal events and cancellation. It creates ZIP, TAR, TAR.GZ, TAR.BZ2, GZIP, and BZIP2 from Worker capabilities, and conditionally RAR through protocol 1.23. The standalone WPF shell remains a separate proof surface rather than shared Explorer UI code.
- New creation is unencrypted, single-output, and absent-destination-only. ZIP Rebuild Copy is the sole opened-session write route and always publishes a distinct complete copy while preserving the original. Directory-tree input is not a generic drag-in or in-place update capability. Rain must keep unsupported copy/drag-in, overwrite, replacement, split, encryption, XZ, and 7z creation affordances disabled. RAR likewise remains disabled unless the exact conditional encoder capability is currently `Available`.
- The worker validates every filesystem/archive path and owns source leases, staging, cleanup, and commit. Rain supplies semantic mappings and never opens, compresses, or edits archive bytes itself. Creation currently has no password request because encryption is not supported; future encryption must use secret slots rather than an ordinary request field.

## Copy, drag, and extraction

- Copy/drag out starts a normal Rain Archives extraction operation into a new operation-owned staging/cache target. Rain Explorer’s activity UI observes the same operation ID/events. Password material uses secret slots; destination conflict and risk remain local fail-closed preflight because no Worker decision-continuation contract exists yet.
- Windows drag-out that requires delayed rendering uses an operation/lease; it does not eagerly extract an entire archive on mouse-down. Cancellation and target abandonment release the lease and owned cache.
- Copy/drag in is exposed only when the opened format advertises staged rewrite capability. Rain sends source filesystem paths/handles and desired archive destination paths; the worker performs one complete rewrite transaction. Rain never edits archive bytes itself.
- Archive-to-archive drag is composed as bounded extraction plus staged rewrite. No uncontrolled nested recursion or implicit whole-archive expansion is allowed.

## Operation/activity bridge

- Rain maps `OperationId`, kind, phase, actual/total bytes, entries, current item, throughput, elapsed time, ratio, warning, error, and retryability into its existing activity system. While the client remains active, it preserves every validated event in order and terminal delivery is exactly once per operation event stream; disposing the client explicitly ends presentation delivery. Rain's subscriber must post to its activity/UI dispatcher and return promptly so bounded client backpressure does not stall later IPC reads.
- Archive descriptor warnings `worker.nested_recovery_required` and `worker.nested_inventory_incomplete` describe one worker-startup inventory snapshot, not an individual archive defect. Rain should deduplicate them per worker lifetime and offer a diagnostics/recovery entry point; it must not infer a temporary path, auto-delete a nested/unresolved candidate, or repeatedly present the same warning as though every opened archive created new residue. Creation records with completed disposition receipts are omitted from the attention inventory and use Rain Archives' internal bounded replay-retention policy; Rain Explorer neither chooses nor expands that maintenance authority. Protocol 1.21's independent reopen is the only current non-destructive nested recovery action and still requires fresh exact evidence.
- Password requests use secret slots and a UI prompt; the password is not persisted in Rain’s activity object. A preview owner that creates a slot must explicitly settle it when capability/metadata/presentation policy refuses the item before `OpenEntryStreamAsync` consumes it. Current conflict and risk decisions are local fail-closed preflight, not Worker decision tokens. `AwaitingPassword`, `AwaitingConflict`, and `AwaitingRiskApproval` are forward-compatible enum values only; Rain must not send or expect a decision response until a future additive contract defines immutable operation authority, expiry, replay, and pre-mutation semantics.
- Protocol 1.22 support diagnostics expose only fixed enums, numeric bounds, and booleans. Rain may use them to explain the 32-admitted/one-running/64-retained queue, cancel-only controls, automatic-recovery-disposition support, and same-user Job containment, but the response contains no path, error text, archive/provider text, secret, recovery ID, or action token. `IsSameUserSecuritySandbox=false` must be presented truthfully; diagnostics never authorize recovery or retry.
- Rain cancellation sends the operation cancellation request and keeps the activity pending until terminal cancellation/failure/completion or worker-loss timeout.

## Capability and invalidation rules

- Read-only/writable state is a property of the opened format/provider/session, not the filename extension.
- Rebuild-required add/replace/delete is surfaced as such before work begins. RAR never advertises write capability.
- A provider crash invalidates all sessions owned by that worker. Rain may restart and reopen from persistent locations, but it must not claim that an interrupted write committed unless final output identity proves it.

## Contract additions before Milestone 6

Protocol versions after the current 1.23 foundation still need paged search, true range reads where they are measurably useful, path-based external-preview lease/provenance handoff, conflict/password/risk continuations, any separately approved overwrite/replacement or multi-output contract, archive invalidation events, extraction-staging disposition/presentation, stable former-ancestry restoration beyond independent recovery reopen, and any richer operation-queue controls. Managed creation/rebuild capabilities, conditional RAR creation, creation disposition, narrow nested discard, copy-only independent nested reopen, operation activity, read-only extraction-staging recovery, and fixed support diagnostics now exist, but older historical N/N-1 binaries beyond the retained matrix, direct current-flow accessibility, and remaining physical network/alias qualification stay gates before release. Each addition stays transport/presentation neutral and receives retained-binary compatibility fixtures before Rain Explorer consumes it.
