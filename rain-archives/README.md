# Rain Archives

Rain Archives is SailHub's Windows archive manager and the archive engine intended for Rain Explorer.

For the exact cross-task implementation state, binding decisions, current verification identity,
must-not-undo rules, next action, and full remaining backlog, start with
[`CONTINUATION.md`](CONTINUATION.md).

The current implementation contains the accepted Milestone 1 foundation, six Milestone 2 secure-read slices, the managed ZIP creation/rebuild surface through protocol 1.16, and TAR/TAR.GZ/TAR.BZ2/raw GZIP/BZIP2 creation plus managed capabilities through protocol 1.18. Milestone 4 adds bounded operation activity at 1.19, read-only extraction-staging recovery inspection at 1.20, exact-evidence copy-only nested recovery reopen as an independent root at 1.21, and fixed-field support diagnostics plus an explicit same-user Worker containment decision at 1.22. Milestone 5A through 5G-D add the Activity Center, bounded archive browser, Settings/Presets with managed create/rebuild, properties/safe preview, Recovery Center/support evidence, existing-command context, reconciled WPF presentation, deterministic Windows product identity, and a centralized semantic control system. Protocol 1.23 fixes valid RAR5 directories that omit optional CRC metadata and adds conditional RAR5 creation through the user's separately installed, signed, licensed WinRAR 7.23-through-7.x encoder. All creation publishes one validated archive to a distinct previously absent destination; raw streams accept exactly one ordinary source file. Archive parsing, creation, rebuilding, and recovery mutation run in an on-demand Worker. The Client, diagnostic CLI, WPF App, and Rain Explorer adapter communicate through versioned Contracts and do not reference codecs directly. Current package/test evidence is recorded in `docs/testing.md`; retained performance evidence stays bound to its historical fingerprint in `docs/benchmarks.md`. Physical network/filesystem, direct current-package accessibility/GUI, installation, signing, and publication remain separate.

## Current shape

- `RainArchives.Contracts` — bounded wire protocol and public DTOs.
- `RainArchives.Core` — format detection, read/write provider contracts, session entry hierarchy, and operation models.
- `RainArchives.Security` — Windows path rules, collision detection, resource limits, stable source leases, handle-relative non-reparse source-tree enumeration, pinned output creation, exact source/staging-manifest validation, provenance, new-destination staged commit, local durable creation-recovery journals, bounded completed-receipt retention, and identity-revalidated nested-workspace disposition.
- `RainArchives.Providers.SharpCompress` — managed read adapter plus path-free TAR, TAR.GZ, TAR.BZ2, GZIP, and BZIP2 writers/validators.
- `RainArchives.Providers.Zip` — framework-backed writer for unencrypted ZIP creation and rebuild.
- `RainArchives.Providers.SevenZip` — disabled native-provider adoption gate. The package contains no native 7-Zip asset.
- `RainArchives.Providers.WinRar` — optional Worker-only RAR5 writer over one exact qualified user-installed WinRAR encoder; no WinRAR binary is bundled.
- `RainArchives.Worker` — isolated parser/operation host.
- `RainArchives.Client` — authenticated worker launch and typed IPC client.
- `RainArchives.Cli` — headless end-to-end harness.
- `RainArchives.App` — a Contracts/Client-only WPF shell with bounded archive root/folder navigation, breadcrumbs, history, Unicode search, deterministic duplicate selection, inert text preview, managed archive creation, ZIP rebuild, recovery review, Activity Center, semantic Light/Dark/High Contrast windows and controls, Settings scrolling, and a deterministic multi-resolution Windows icon. Milestone 5 remains partial beyond the completed tranches through M5G-D.

Current recovery hardening groups nested temporary sources beneath one lazily created random worker workspace with a token-bound exclusive liveness claim. ZIP creation separately writes a local, exclusive, append-only recovery journal before destination staging and advances checksummed `Admitted`, `Writing`, `Finalized`, `CommitIntent`, and `Committed` phases around the irreversible rename. The journal binds the operation ID, canonical destination, destination-parent identity, deterministic token-derived staging name, staging identity, and finalized length without recording source paths, contents, or secrets. Later workers perform a bounded scan of at most 1,537 local operation children to publish at most 1,024 unresolved/active/suspicious attention records, never contact recorded destinations during startup, and expose only count/path-free warnings; unresolved, malformed, active, or suspicious candidates are never auto-deleted. Protocol 1.9 adds a fresh path-free inventory request plus explicit read-only inspection of one opaque recovery ID. Protocol 1.10 adds feature `archive-creation-recovery-disposition-v1`: after inspection, an explicit caller may commit one exact `CommitIntent` staging artifact, discard one identity-bound staging artifact, accept one exact published final, or acknowledge that no owned artifact remains. Every request repeats the inspected phase, sequence, and UTC journal timestamp, and stale state is refused before mutation. Security exclusively reparses the journal, pins and rechecks the destination ancestry, freshly validates artifact identity, length, kind, reparse state, and hard-link count, keeps the exact staging handle pinned with write/delete sharing denied, and uses a no-replace relative rename for commit. A checksummed two-frame receipt is durably flushed at `Intent` before mutation and at `Completed` after the required postcondition; same-action replay returns `AlreadyCompleted`, while a conflicting action or malformed receipt fails closed. Completed receipts are a bounded replay cache: Rain keeps the newest 256 for at most 30 days, attempts one count-prune after each new resolution, and prunes at most 256 during worker startup. Count pruning requires a complete bounded scan; truncated scans never use rank as deletion authority. Age or count pruning exclusively reopens the exact ordinary two-file operation tree without following reparses, requires matching enumeration identities and one hard link per file, rechecks the tree immediately before handle-relative deletion, and never contacts or deletes a recorded archive destination. A pruned replay returns path-free `recovery.not_found` without destination access. Protocol 1.11 adds feature `nested-workspace-recovery-v1`: list and inspect disclose only opaque lowercase-hex IDs, counts, byte totals, timestamps, and a metadata revision; no temporary path crosses IPC. Explicit discard requires the exact inspected revision, source count, total bytes, and repeated recovery-ID confirmation. Security reopens the exact-case workspace and every descendant through no-follow handles, requires stable nonzero identities, ordinary non-reparse one-link owner/source objects with no named streams, at most 16 sources, at most 256 MiB per source, and at most 512 MiB total, then revalidates the complete shape immediately before mutation. Cancellation is honored until the first deletion and then deferred through the bounded leaf-to-root sequence. A hard kill after the first exact source deletion leaves a smaller suspicious tree that a fresh ordinary Worker reports and preserves; there is no automatic nested deletion, restore, or retry. The CLI exposes both recovery families. The WPF Recovery Center now presents them as separate tabs without sharing filesystem authority: creation listing stays path-free until explicit Inspect reveals escaped destination evidence, while nested listing and confirmation never disclose a temporary path. Refresh, selection change, refusal, cancellation, failure, or an uncertain result clears mutation authority as applicable and never triggers an automatic retry. Closing the dialog cancels and drains both view models before the main shell resumes. The wrapper invokes the production `WorkerProgram`, authenticated named-pipe handshake, `WorkerHost` request path, and Security routine; only synchronous checkpoint callbacks are test-only, and the shipping Worker has no probe switch. The interrupted client observes `worker.disconnected`; a fresh ordinary Worker reconciles creation intent exactly once or conservatively preserves the partial nested tree. ## Diagnostic CLI

```powershell
rain-archives list archive.zip --worker .\RainArchives.Worker.exe
rain-archives test archive.zip --worker .\RainArchives.Worker.exe
rain-archives extract archive.zip .\new-output --worker .\RainArchives.Worker.exe
rain-archives create-zip .\new.zip --preset balanced --file .\photo.jpg Photos/photo.jpg --worker .\RainArchives.Worker.exe
rain-archives create-zip .\new.zip --preset maximum --directory .\Project Project --worker .\RainArchives.Worker.exe
rain-archives create-tar .\new.tar --preset store --directory .\Project Project --worker .\RainArchives.Worker.exe
rain-archives create-tar-gz .\new.tar.gz --preset balanced --file .\photo.jpg Photos/photo.jpg --worker .\RainArchives.Worker.exe
rain-archives create-tar-bz2 .\new.tar.bz2 --preset balanced --directory .\Project Project --worker .\RainArchives.Worker.exe
rain-archives create-gzip .\photo.jpg.gz .\photo.jpg --preset maximum --worker .\RainArchives.Worker.exe
rain-archives create-bzip2 .\photo.jpg.bz2 .\photo.jpg --preset balanced --worker .\RainArchives.Worker.exe
rain-archives recovery-list --worker .\RainArchives.Worker.exe
rain-archives recovery-inspect <recovery-id> --worker .\RainArchives.Worker.exe
rain-archives recovery-apply <recovery-id> discard-owned-staging --expected-phase Writing --expected-sequence 2 --expected-recorded-at <UTC-O-timestamp> --confirm <same-recovery-id> --worker .\RainArchives.Worker.exe
rain-archives nested-recovery-list --worker .\RainArchives.Worker.exe
rain-archives nested-recovery-inspect <recovery-id> --worker .\RainArchives.Worker.exe
rain-archives nested-recovery-discard <recovery-id> --expected-revision <64-lowercase-hex> --expected-source-count <count> --expected-total-bytes <bytes> --confirm <same-recovery-id> --worker .\RainArchives.Worker.exe
rain-archives nested-recovery-reopen <recovery-id> <source-id> --expected-revision <64-lowercase-hex> --expected-source-count <count> --expected-total-bytes <bytes> --expected-source-length <bytes> --expected-content-sha256 <64-lowercase-hex> --worker .\RainArchives.Worker.exe
rain-archives support-diagnostics --worker .\RainArchives.Worker.exe
```

Extraction and every creation command accept only a destination that does not exist. Passwords are accepted for read operations through an interactive prompt or `--password-stdin`; no creation route accepts encryption or a password. ZIP accepts zero to 4,096 explicit/tree material entries; TAR, TAR.GZ, and TAR.BZ2 accept bounded explicit/tree input; raw GZIP/BZIP2 accept exactly one ordinary source file and derive their synthetic member name from the destination stem. TAR is Store-only, GZIP-backed formats support all four presets, and BZIP2-backed formats support Balanced only. Directory roots and empty directories are preserved only by archive formats, reparses are refused, and existing archives are never overwritten or updated. `recovery-apply`, `nested-recovery-discard`, and `nested-recovery-reopen` require exact freshly inspected evidence; none accepts an arbitrary temporary path, overwrite target, automatic choice, or retry request. Reopen copies and redetects one exact source as a new independent root. `support-diagnostics` prints only fixed policy fields and grants no recovery authority.

## Product boundaries

- No account, cloud requirement, advertising, telemetry by default, or persistent background service.
- RAR creation is conditional on one separately installed signed x64 WinRAR 7.23-through-7.x encoder at its exact Program Files path; Rain does not bundle, install, update, or rediscover that binary.
- No ZIP/TAR/raw/RAR creation encryption, 7z creation, XZ creation, split output, overwrite, replacement, or in-place update at the current gate.
- No provider may write directly to the selected extraction destination.
- No writer provider receives source or destination filesystem paths; it receives only validated metadata and caller-owned streams.
- Every archive modification will be a staged rewrite until a separately reviewed transactional design proves otherwise.
- Rain Explorer will reference only Contracts and Client.
