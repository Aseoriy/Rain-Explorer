# Rain Archives security policy

Every archive is untrusted input. A normal-looking archive name, extension, or generating application does not make its content trusted.

## Enforced foundation rules

- Parsing and decompression run in an unelevated worker process.
- The client creates a per-logon named pipe with a random name, authenticates the launched worker with an inherited bootstrap value, verifies its PID, and places it in a kill-on-close Job Object.
- Passwords use one-time binary secret slots with atomic create/store/consume/discard state. Open, preview-stream, extraction, and integrity requests settle a supplied slot on every local-validation, worker-admission, queued-cancellation, success, and failure path; ownership transfers to a stream/background operation only after its admitted task exists. Extraction and integrity settle the Worker slot and zero their local password before publishing any terminal event. An authoritative cancelled Open response already proves Worker settlement, so Client does not queue a redundant discard behind cancelled indexing; local/pre-send failures retain explicit discard cleanup, while transport failure closes the owned Job and lets Worker shutdown clear all slots. The WPF preview owner explicitly discards a temporary slot after every accepted, refused-before-read, failed, or cancelled presentation attempt. Passwords are not accepted as command-line arguments and are not serialized into ordinary JSON messages.
- Read providers expose metadata and entry streams. They cannot choose extraction paths and their extract-to-directory helpers are not used. Writer providers receive validated archive-relative metadata, already-open source streams, and a caller-owned destination stream; they never receive source or destination filesystem paths.
- Integrity/extraction copies use provider checksum validation into a Rain-owned guarded output stream. Raw GZIP additionally verifies decoded size plus trailer CRC32/ISIZE, while compressed TAR performs one bounded, cached full outer-stream validation before the first integrity/extraction copy. A raw preview stream is never treated as proof of archive integrity.
- An open session holds a deny-write/delete source lease and also checks file identity, length, last-write time, and a prefix hash. Multipart signals may classify an archive as list-only, but never authorize integrity testing or extraction; those operations remain refused until all volumes can be leased and fingerprinted.
- Archive paths are parsed as relative component lists. Absolute, UNC, device, drive-relative, traversal, ADS, reserved-device, trailing-dot/space, and invalid Unicode names are refused.
- Collision checks use Unicode NFC plus case-insensitive Windows comparison. Duplicate, file/directory, case, and normalization collisions never use silent first-wins or last-wins behavior.
- ZIP creation accepts explicit regular files from fully qualified ordinary Windows drive or UNC filesystem paths. Protocol 1.8 may additionally accept bounded directory roots paired with nonempty archive-relative roots. Relative, device, drive-relative, ADS, reserved-device, trailing-dot/space, and reparse sources are refused. Every source ancestry is opened without following reparses; directory children are enumerated and reopened relative to pinned native directory handles; regular files are held with write/delete sharing denied; and identity, length, and last-write time must match the validated plan. Empty directories are preserved, but links and reparses are never followed. Actual remote-server creation behavior remains a separate acceptance gate.
- Archive links and reparse metadata are listed but not materialized.
- Milestone 1 writes a complete random, operation-owned same-volume staging tree and renames it only after success. Existing destinations are refused. Staging directories and files are created relative to pinned, verified Windows directory handles; the final no-replace rename is also relative to the pinned parent handle. A reparse, identity replacement, or destination race detected by these checks fails closed instead of redirecting output or overwriting a target.
- Timestamps and download provenance are applied through pinned file/parent handles. Before commit, every expected descendant is reopened relative to pinned handles and checked for type and file identity; regular files must have exactly one hard link. Path enumeration must equal the operation manifest with no extra, missing, or reparse entries, then handle/identity validation is repeated. Cleanup recurses only when the random staging path still has the identity created by the operation and the tree contains no reparses; suspicious staging is preserved for manual recovery.
- Protocol-1.7/1.8 ZIP creation requires a nonexistent destination beneath an existing non-reparse parent. It records one random-token sibling staging name in the local durable journal, then creates that file relative to pinned ancestry. The ordinary path immediately marks that exact handle with a reversible delete disposition. When every regular source has one unanimous valid security zone, Rain first creates and identity-checks an empty `Zone.Identifier` through the pinned parent, retains that stream with only delete sharing, and then marks the base file for deletion. After durable archive flush and exact final source/provenance validation, Rain writes, flushes, and reads back only canonical zone data through the retained stream, closes it, verifies the base identity and link count, records final length and commit intent, clears the disposition, performs a handle-relative no-replace rename, and records committed state. Protocol 1.8 also re-enumerates every selected directory tree and compares its complete path/kind/identity/length/timestamp manifest immediately before destination commit checks. Ordinary failure or cancellation closes the still-delete-pending handles and removes only proven journal state; a destination race or source mutation fails without overwriting the raced file.
- Protocol 1.17/1.18 applies the same Security-owned single-output transaction to TAR, TAR.GZ, TAR.BZ2, raw GZIP, and raw BZIP2 without changing ZIP wire shapes or granting provider filesystem authority. TAR-family input uses the same pinned non-reparse explicit/tree planning and 4,096-entry/64-GiB bounds; raw formats accept exactly one ordinary regular source file and no directories or additional inputs. TAR metadata is separate from ZIP DOS semantics: only regular files/directories and qualified UTC timestamps are admitted, while pre-Unix timestamps and Windows attributes are refused.
- Every staged creation manifest binds each regular file to the SHA-256 collected through the authoritative source-copy stream. Format-specific readback must consume the complete staged output and compare kind, name, length, timestamp where applicable, and decoded payload digest. TAR validates complete structure/footer; compressed TAR additionally validates the outer stream; GZIP validates its trailer; BZIP2 decodes exactly one member, requires complete underlying-stream consumption, validates its footer, and rejects trailing bytes or concatenated valid members. RFC-1952 raw-GZIP MTIME zero is represented as unavailable rather than fabricated as the Unix epoch; nonzero values retain their actual timestamp. Writer finalization is one-shot even when it fails; cleanup cannot retry footer emission.
- Output estimates are format-specific and conservative. The existing ZIP estimate is unchanged. TAR-family estimates charge each 512-byte entry header, payload rounded to a 512-byte block, two EOF blocks, and bounded PAX/extended-header overhead before the guarded output/disk checks. Raw streams retain the one-source byte ceiling plus compressor overhead. Runtime guarded-stream accounting, destination-space checks, source revalidation, durable journal phases, and no-replace commit remain authoritative.
- Protocol 1.9 recovery listing reads only the bounded local journal root and returns opaque IDs plus path-free metadata. Explicit inspection of one ID is the only read-only recovery request allowed to expose or contact its recorded destination. It holds the journal exclusively, reparses it before access, opens destination ancestry and direct artifacts without following reparses, and reports identity/length/type/link evidence without reading file content or mutating the filesystem. A torn or conflicting record cannot become ownership authority, and inspection alone authorizes nothing. Protocol 1.10 adds the only request allowed to mutate a recorded archive artifact: an explicit caller must select one named action and repeat the exact inspected phase, sequence, timestamp, and recovery ID confirmation. Security then reparses the journal, reopens and rechecks parent ancestry and direct artifacts, refuses stale/conflicting/suspicious evidence, pins the exact staging handle without write/delete sharing, revalidates identity/length/link count immediately before mutation, and either performs one no-replace relative commit, deletes that exact proven staging file, or records one applicable no-mutation resolution. Completed receipts are local Rain-owned replay metadata, not archive artifacts: the newest 256 are retained for at most 30 days, with bounded maintenance after resolution and at worker startup. Pruning requires a fully parsed `Completed` receipt, an exact ordinary two-file operation tree, matching handle-relative enumeration identities, exclusive no-follow handles, and one link per file. Count-based pruning is disabled when the bounded scan is truncated. Active, malformed, hard-linked, reparse, incomplete, inaccessible, or unexpected state is preserved; pruning never opens a recorded destination. Once the first metadata delete begins, cancellation is deferred through the bounded exact-tree sequence so cancellation cannot intentionally manufacture a half-pruned tree.
- Declared sizes and counts are untrusted. Checked arithmetic, provider and synthetic-entry budgets, a 256-component hierarchy limit, a default 64 GiB decoded-output ceiling, declared/runtime ratio checks, actual streamed byte accounting, exact completed-size checks, and destination-space reserves are required. Space preflight and runtime checks charge conservatively for the staging root, directories, regular files, and provenance streams; a separate object counter forces a fresh space check at least every 1,024 created objects even when payload bytes are tiny.
- ZIP and TAR-family creation admit at most 4,096 material archive entries after directory expansion and at most 64 GiB of regular-file source bytes. The explicit-file-only route may be empty; a directory-tree request requires at least one directory root. Raw GZIP/BZIP2 admits exactly one ordinary regular source file of at most 64 GiB. Rain computes a checked format-specific conservative output ceiling, preflights destination space, and enforces output and space again while bytes are written. Archive paths receive the same component/depth/length, case-insensitive NFC collision, duplicate, parent-spelling, and file/directory-prefix checks before staging exists.
- Valid source Mark-of-the-Web zones are copied to regular extracted files as a canonical `Zone.Identifier`; untrusted URL fields are discarded. The reader accepts only one `ZoneId` from 1 through 4 inside a `[ZoneTransfer]` section. A missing section, out-of-range value, or duplicate/conflicting `ZoneId` makes the provenance unusable rather than selecting a convenient value. New ZIP creation propagates only a unanimous valid zone from every regular source. Mixed, missing-plus-present, malformed, or inaccessible states omit the output stream and emit at most one sanitized provenance warning; all-absent or all-unsupported states make no preservation claim and emit none. Valid-size source ADS content receives exact length/hash revalidation; oversized malformed streams retain length plus a bounded 4 KiB prefix hash and are never propagated. A destination that cannot prepare the ADS commits without it and produces one structured warning.
- Protocol messages are serialized once into a bounded writer, reject unknown JSON members, are feature-negotiated, and use contiguous request plus operation-event sequences. Listing pages have an encoded-byte budget so one response cannot exceed the 1 MiB frame limit. The client accepts events only for operation IDs authorized by successful start responses; malformed output, invalid payloads, unknown operations, or post-terminal events abort the authenticated transport and its owned worker. While the client remains active, the bounded presentation queue preserves every validated event in order and applies backpressure instead of discarding progress or warnings; explicit disposal ends presentation delivery. A warning event is provisional operation information and may be followed by authoritative cancellation/failure; only the terminal event establishes whether a destination was committed. Protocol 1.23 retains every minor-1 through minor-22 feature and wire shape. Minor 17 adds distinct TAR explicit/tree/capability messages; minor 18 adds distinct TAR.GZ/TAR.BZ2 explicit/tree, raw GZIP/BZIP2, and managed-capability messages; minor 19 adds only bounded operation activity; minor 20 adds only extraction-staging recovery inventory and explicit read-only inspection; minor 21 adds exact-evidence independent nested recovery reopen; minor 22 adds fixed-field support diagnostics; minor 23 adds distinct conditional RAR explicit/tree/capability messages. Each feature carries explicit dependencies; a downgraded Client refuses locally before sending a frame, and a downgraded Worker refuses the message kind before payload parsing or filesystem access. Minor 22 negotiates no RAR creation feature. Retained 1.17 and exact 1.18 binaries plus current source prove prior common operations and newer pre-access refusal in both directions. A dedicated worker- and client-bounded control lane can cancel accepted cancellable requests without abandoning their authoritative response. Recovery destination inspection or disposition may block inside synchronous Windows/network filesystem I/O; after the bounded cancel handshake, a separate two-second response deadline tears down only the authenticated worker owned by `RainArchives.Client`. Raw protocol consumers must provide equivalent containment. Physical blocked-UNC recovery cancellation remains unverified. If a bounded cancel/discard/compensating-close/worker-close acknowledgement does not arrive, the client fails all pending requests, closes the authenticated pipe, and closes only its worker-owning kill-on-close Job Object. Physical frame writes are never interrupted halfway.
- Protocol-1.19 activity snapshots are connection-lifetime status only, not recovery or filesystem authority. They expose at most 32 active/queued and 64 retained terminal operations, with one concurrent execution and no pause, retry, reordering, or restart persistence. Records contain only an operation ID, typed kind/phase, successfully sent event sequence, canonical UTC lifecycle timestamps, numeric progress, a warning count, and cancelability. Source/destination/temp paths, entry IDs/names, warning/error text, secrets, recovery IDs, provider details, and untrusted archive text are absent. Worker snapshot publication is ordered with event frames under the authenticated write gate; Client rejects duplicate IDs, invalid lifecycle/order/timestamps/progress, and each individual bound by aborting only its owned transport/Worker.
- Protocol-1.20 extraction recovery is read-only evidence, not cleanup or retry authority. Every tracked extraction appends five bounded checksummed full-state journal phases under a local fixed-drive root: `Admitted`, `Writing`, `Finalized`, `CommitIntent`, and `Committed`. Startup examines only that local root, never contacts a recorded destination, and publishes only opaque IDs, conservative phase/state, bounded counts/timestamps, and incomplete/suspicious flags. Explicit inspection of one strict ID reparses the journal before destination access, opens exact-case ancestry and direct staging/final names through pinned no-follow handles, and verifies stable nonzero parent/root/object identities, ordinary type, one-link files, reparse/ADS shape, count/byte/depth ceilings, and a SHA-256 content-bound tree revision. Aggregate bytes include every unnamed file stream and allowed `Zone.Identifier`; the revision includes hashes of both. Active, torn, changed, excessive, malformed, inaccessible, or ambiguous state is preserved. Ordinary cleanup also preserves staging when validation finds any unexpected path, hard link, named stream, reparse, replacement, or unavailable identity. The response fixes mutation, retry, and cleanup capabilities false; there is no disposition message, automatic retry, recursive cleanup, restore, replacement, or WPF action.
- Protocol-1.21 independent nested recovery reopen is copy-only and grants no deletion authority. One request repeats the fresh workspace revision/count/bytes and exact source ID/length. Security exclusively reparses and pins the inactive exact-case workspace, revalidates owner/source ancestry, liveness, stable identities, ordinary type, one-link/no-reparse/no-ADS shape, bounds, and content evidence, and denies source write/delete sharing while it is copied. The Worker flushes a new owned source, redetects its contents, and returns a fresh depth-zero root with zero ancestry-chain bytes and no former parent/source link. It never exposes or adopts the recovery path and leaves the original bytes/evidence unchanged. A smaller, missing, partial, changed, or ambiguous recovery tree is never success evidence or retry authority.
- Protocol-1.22 support diagnostics are a closed fixed schema of enums, integers, and booleans. They expose only policy/capability facts and explicitly set `IsSameUserSecuritySandbox=false`; they contain no paths, filenames, archive/provider text, exception message, secret, recovery ID, or action token. Standard Worker exceptions map to fixed redacted messages and a diagnostic UUID. `ArchiveProviderException.Message` is forwarded across the error seam, so provider messages must remain fixed or policy-sanitized; generic exception text, native stdout/stderr, filesystem paths, secrets, and archive-controlled control text are forbidden in provider errors, activity, and support evidence.
- Operation activity remains cancel-only. Start admission is 32, execution is one, terminal retention is 64, and queue ordering is explicitly unspecified. The 33rd start fails before handoff and settles its secret; terminal operations refuse cancellation. `AwaitingPassword`, `AwaitingConflict`, and `AwaitingRiskApproval` are forward-compatible validation values only and are never emitted. Passwords remain one-shot slots, conflicts/risk remain local fail-closed preflight, and `IsRetryable` is advisory. There is no retry/pause/reorder/decision/restart-persistence endpoint. Pre-response start cancellation uses bounded teardown of only the authenticated Client-owned Worker when no operation ID can be recovered; post-response cancellation targets that exact ID.
- The Milestone-5A Activity Center is presentation-only and keeps the same authority boundary. WPF consumes Contracts/Client snapshots, events, cancellation, and fixed-field diagnostics; it has no Worker/Core/Security/provider or filesystem reference. It escapes live current-entry text, discards warning/error/provider messages, displays only typed terminal category, and never derives a path, recovery ID, secret, action token, or mutation authority. Cancel is hidden unless the newest validated snapshot authorizes the exact operation ID, and a local pending or terminal state immediately suppresses stale authority. One bounded non-overlapping refresh owner serializes activity and diagnostics, caps state at 96 records, coalesces UI work away from Client event receipt, rejects stale generations, stops on offline/downgrade, and is cancelled/drained before Client disposal. It persists no history and performs no automatic retry. Automated system-color, keyboard, focus, automation-name/help/live-status, DPI-layout, and recycling-virtualization checks do not replace current-package manual visual or assistive-technology acceptance.
- The Milestone-5B archive browser is also presentation-only. It receives validated Contracts descriptors from Client pages and independently rejects a count mismatch, duplicate/empty ID, missing or non-directory parent, self-parent/cycle, excessive hierarchy, invalid metadata, or persistent key that was absent, duplicated, malformed, or returned without negotiation before replacing the current browser state. Parent-chain validation is iterative: one reusable path plus visited/depth maps detects cycles and applies the exact 256-level limit without an input-proportional call stack; it is O(n) time/memory within the 500,000-descriptor cap. The browser materializes at most 512 WPF rows, retains at most 256 navigation locations, and uses recycling virtualization. `EntryId` is session-local; `(NormalizedPath, DuplicateOrdinal)` is only a presentation-resolution key and never path or mutation authority. Navigation/search/selection restoration occurs only after an explicit same-canonical-source reopen, exact fingerprint equality, persistent-key negotiation on both sessions, a previously trustworthy browser state, and authoritative prior-session close. Once that close begins, any failed or non-authoritative replacement clears the old session/browser authority. Stale, changed, malformed, offline, unsupported, cancelled, or downgraded state never restores or retries automatically. Names, methods, formats, breadcrumbs, automation labels, and status omit provider/error text and visibly escape untrusted control/format text; preview remains bounded inert read-only text. WPF still has no Worker/Core/Security/provider authority.
- Milestone 5C keeps archive and destination authority out of WPF while adding App-private UI persistence. The version-1 settings document is limited to one managed-format enum, seven compression-preset enums, and one boolean; it has a 32 KiB file ceiling and no free-form string slot. Unknown, missing, duplicate, malformed, truncated, invalid-Unicode, invalid-enum, and future-version state is refused. A valid backup is usable only as read-only last-known-good hints: ordinary Save remains disabled until explicit Reset repairs the primary. The existing ZIP preset document remains limited to 64 user records, an exact 128 KiB ceiling, NFC names of at most 64 scalars/256 UTF-8 bytes, fixed metadata fields, and no archive/source/destination text; required and duplicate JSON members are strict. Both stores use a private LocalAppData chain, per-user mutex, ordinary no-reparse/one-link/no-ADS object checks, random `CreateNew` sibling staging, durable flush, atomic replace-or-first-move, validated backup, and exact staged-identity cleanup. Malformed, future, oversized, unavailable, or unsafe state cannot be silently migrated: ordinary preset Save revalidates under the mutex, and Create/Rebuild carry the exact load state and recheck immediately before Save/Remove. Built-ins remain usable, but only Settings Center's explicit Reset may repair refused storage. The two documents are independently atomic rather than transactional, so partial save/reset is reported and requires review/reload. Shutdown cancels and drains serialized settings/capability work. Saved defaults are hints only: all six managed creation formats and eligible ZIP Rebuild Copy repeat current authenticated capability validation before start. Raw GZIP/BZIP2 retain exactly-one-ordinary-file policy; all outputs remain distinct, absent, no-replace copies and every original/source is preserved. No path, entry text, secret, recovery ID/revision, operation record, provider/error text, temporary path, handle, identity, overwrite/retry/decision authority, or native-provider control is persisted.
- Milestone 5D keeps properties and preview presentation inside the same Contracts/Client-only boundary. Archive and selected-entry properties are fixed projections of already validated descriptor/capability fields; optional sizes, ratios, timestamps, attributes, link, duplicate, encryption, integrity-presence, and persistent-key state appear only when mathematically and structurally valid. Every one-based duplicate occurrence widens the validated non-negative `Int32` ordinal to `Int64` before addition, so the maximum ordinal renders as the positive `2,147,483,648` in both visible and Automation output. Provider identifiers/text, compression-method text, link targets, raw integrity values, source fingerprints, exceptions, secrets, recovery IDs, cache/temp paths, handles, command lines, and mutation authority are never projected. The preview service returns only typed text/binary/oversize/unsupported outcomes, exact source-read/byte facts, and an encoding enum after strict UTF-8 or BOM-proven UTF-16/UTF-32 decoding. NUL-bearing, invalid, ambiguous, and control-dense content is inert; HTML/script, embedded objects/macros, shell/Open With, implicit export, and automatic external launch remain closed. Presentation reads at most 1 MiB plus one detection byte, owns at most four materializations with one active plus the newest pending request, rejects stale generations, cancels/drains on selection/source/session/close, and relies on the existing exclusive delete-on-close cache lease without exposing its path. Malformed projection/result shapes fail closed without replacing the prior authoritative view.
- Milestone 5E consolidates creation, nested-workspace, extraction-staging, and fixed support evidence in one modal Contracts/Client-only Recovery Center without creating recovery authority. All inventories remain bounded, local, path-free, and non-destructive until the user explicitly inspects one opaque record. Creation keeps only its protocol-1.10 exact disposition actions and default-No confirmation; nested recovery keeps only exact-evidence independent depth-zero reopen and discard; extraction remains strictly read-only and exposes no action. Refresh, selection change, malformed/downgraded/offline state, cancellation, and uncertain completion invalidate presentation authority. Supplied one-shot password-slot ownership transfers at Client route entry: validation, lifecycle-gate cancellation, and every other pre-response failure settle each slot exactly once, while an authoritative success remains Worker-consumed. An adopted recovered archive uses a fixed title and a fresh session descriptor/list; no temporary path or former ancestry enters the shell. The dialog service owns a reopened session until successful result handoff, and the MainWindow owns it until the complete authoritative state transition, including notifications, succeeds; every earlier cancellation, drain/callback failure, or transition failure closes that exact session once. Ordinary open follows the same pre-commit compensation rule. Dialog initialization and every child request are cancelled and fully drained before return. Support evidence maps only protocol-1.22 fixed enums, integers, and booleans. Provider/exception text, archive-controlled text, secret material, recovery or cache paths, command lines, generic cleanup/delete, restore, retry, replacement, and extraction disposition controls remain absent. Destination text appears only after explicit typed inspection and is visibly escaped; opaque IDs are exact protocol evidence and are never converted into paths. Automated system-color, access-key, focus, Automation name/help/live-status, DPI-layout, and recycling-virtualization checks do not replace exact-package manual accessibility acceptance.
- Milestone 5F adds no command or filesystem authority. One fixed-field `ArchiveCommandContext` derives every mouse/keyboard affordance from the newest validated archive descriptor, browser state, busy state, current bounded visible page, and canonical `EntryId` resolution. A substituted or stale view-model object cannot become authority: duplicate visible identities fail closed, missing identities are discarded, and each handler re-resolves its primary or selection immediately before invoking the existing navigation, properties, bounded safe-preview, integrity, or extraction route. The context is limited to 512 visible rows; the existing 500,000-entry index, 256-location history, protocol paging, 1 MiB preview, and Worker containment bounds do not change. The properties/safe-preview inspector starts hidden and is revealed only by an authorized Properties or Safe Preview command. Its fixed keyboard-accessible Close control invalidates the preview generation, cancels active and pending work, joins the bounded preview pump, clears presentation only after drain, and then requests focus for the current archive entry list/selection; a late completion cannot repaint the closed surface. Session/source/state transitions use the same cancellation/drain boundary or retain only the existing explicit fixed offline/stale preview state. No window-global Escape binding is added. Menu labels, help, live status, and availability text are fixed and path/provider/archive/secret/recovery-free. Generic Open With, export, external launch, shell execution, delete/rename/add or other mutation, overwrite/replacement, retry, restore, recovery actions, and provider-specific commands remain absent. WPF still references only Contracts and Client; protocol 1.22 and all Worker/Security checks remain authoritative.
- Milestone 5G-A is a main-shell presentation change only. Light, Dark, and High Contrast palettes plus shared spacing, typography, focus, control, card, DataGrid, and static vector-icon resources remain inside the App; WPF still references only Contracts and Client. System mode reads the per-user Windows app-theme preference without changing it, explicit Light/Dark is process-local, and Windows High Contrast always selects solid dynamic `SystemColors`. The redesigned header, command/navigation hierarchy, bounded virtualized entry list, wrapping welcome surface, adaptive inspector, and single status live region add no protocol, dependency, provider, filesystem, recovery, secret, mutation, overwrite, retry, shell, or external-launch authority. Archive-controlled entry names remain visibly escaped; row Automation text adds only already validated typed safety/encryption facts and never raw provider, error, path, secret, or archive fields. The 500,000-index, 512-visible-row, 256-history, protocol paging, preview/cache, Worker-containment, no-overwrite, cancellation/drain, session-handoff, and inspector focus-restoration rules are unchanged. Automated resource, XAML, UI Automation, min-size, package, and product-flow checks do not replace exact-package visual, Narrator, keyboard-only, High Contrast, 100/150/200%, mixed-DPI, or clean-machine acceptance.
- Cleanup is never a generic name-based sweep. Stream/parser state dies with its exact lease/session; preview is capped at eight delete-on-close leases/512 MiB; activity retains 64 in-memory terminals; nested storage is capped at 16 sources/512 MiB and removes exact identities on normal close; extraction/creation/rebuild remove only freshly revalidated owned staging/journals on normal settlement. Only verified creation `Completed` metadata has automatic newest-256/30-day retention deletion. Recovery inventory publishes at most 1,024 records per family. Active, changed, malformed, identity-unavailable, excessive, inaccessible, partial, hard-linked, reparsed, streamed, or ambiguous state has no age/count deletion authority and remains preserved. Active allocation and inspection work are bounded, but unverified disk evidence intentionally has no destructive retention deadline because deleting it would violate that preservation boundary.
- Archive-controlled text is presentation data, not terminal or UI control input. The CLI and WPF shell visibly escape control/format characters, bidi controls, line separators, invalid UTF-16, and backslashes before display while retaining the original provider-neutral value for IDs, search, selection, and extraction. The WPF entry-text presenter accepts only strict UTF-8 or BOM-marked UTF-16/UTF-32, rejects NUL-bearing, invalid, and control-dense payloads, preserves only CR/LF/tab controls, and never invokes active-content or external handlers.
- The WPF creation-recovery center may list only path-free summaries until the user explicitly inspects one opaque record. It derives action buttons solely from that fresh typed inspection, visibly escapes destination/evidence text, uses no arbitrary path input, and requires a separate default-No confirmation before sending the exact inspected revision. Declined confirmation sends nothing. Any cancelled, failed, stale, or uncertain disposition clears action authority and is not retried or changed automatically; closing the dialog cancels and drains its active Client request before ordinary shell work resumes. Inspection-only workers expose no mutation affordance.
- The WPF nested-workspace recovery tab remains path-free through listing, inspection, confirmation, and completion. Only one freshly inspected `VerifiedDisposable` response with a lowercase SHA-256 revision, protocol-bounded source count, and protocol-bounded byte total can enable Discard. Selection change, refresh, cancellation, failure, malformed evidence, or any non-disposable assessment clears that authority. A separate default-No confirmation repeats the opaque ID, revision, source count, byte total, and partial-deletion caveat; it never contains the Worker temporary root. The App forwards those exact values once, does not retry an uncertain result, and leaves every active, suspicious, incomplete, identity-unavailable, or changed workspace untouched.
- Seek-only preview consumers use a client-owned cache over the authenticated complete-entry stream. The caller supplies an existing non-reparse cache directory; each payload uses an unguessable `CreateNew` file held with `FileShare.None` and delete-on-close. After terminal completion and declared-length validation, Rain rewinds that same exclusive handle and publishes only a read-only seekable wrapper, avoiding a path-based reopen. Default admission is 512 MiB across at most eight active leases. The WPF text policy lowers this to 1 MiB per item plus one detection byte and four materialization slots, then serializes UI requests to one active plus one newest pending request. Closing the stream, lease, cache, panel, archive, or app releases reservations and attempts every cleanup step; the cache never recursively enumerates or deletes its root or unrelated content, and it does not expose a cache path as a public contract.
- Nested archive materialization is explicit and stays in a lazily created worker-owned random workspace beneath the trusted temporary root. A token-bound `owner.lock` is held exclusively while that worker is alive; each child source is immutable after materialization and has exact handle-relative cleanup. Later workers inspect at most 1,024 matching direct children, distinguish active, token-verified unlocked, and suspicious/unreadable state, and emit only count-based/path-free warnings. Startup inventory never deletes or recursively traverses a candidate workspace. Explicit independent reopen revalidates one exact source and copies it into a new depth-zero session without mutating or exposing the candidate workspace.
- The worker is never elevated. The accepted current containment design is the authenticated exact-PID same-user Worker plus one-process/2-GiB kill-on-close Job Object. It contains crashes and bounds owned lifetime/resources but is not a same-user filesystem sandbox. AppContainer/brokered handles remain unsupported until a compatible maintained principal/ACL/handle-broker and atomic deployment design is separately proven.

## Known limits at the current gate

- The worker runs with the same user token and can access anything that user can access. A compromised native/managed parser is not contained from same-user file reads. Milestone 4 retains this as an explicit lifecycle/crash containment limitation; AppContainer or handle brokering is not enabled without a separately proven compatible authority and deployment design.
- App-private settings hardening is an accidental-corruption and ordinary filesystem-safety boundary, not a hostile same-user sandbox. Directory creation, ADS enumeration, and final `File.Replace`/first `File.Move` remain path-based and cannot transactionally seal every ancestry component against a malicious process with the same user token between checks. Stable identities, one-link/no-reparse/no-ADS checks, fresh unguessable `CreateNew` siblings, durable flush, precommit revalidation, and exact cleanup fail closed for ordinary races without granting archive/destination authority. A different-principal broker, private ACL/handle-relative namespace design, and separately maintained deployment contract are required before claiming stronger same-user tamper resistance.
- Passwords must become a managed `string` for the current SharpCompress API. Binary buffers are zeroed where possible, but immutable managed copies cannot be reliably zeroized.
- A hard process kill before extraction commit can leave a journal-bound operation-owned staging directory. A kill after a same-volume rename can leave a complete final destination even if the client never received the terminal event, so callers must inspect rather than retry blindly. Protocol 1.20 brackets those states with durable extraction phases and lets a later worker list them path-free and explicitly inspect one without mutation. A real authenticated exact-PID test kills the owned Worker after authoritative extraction progress, then proves that restart reports the `Writing` record and unchanged staging tree without cleanup or retry. An isolated exact-PID test separately proves that a hard-killed nested worker leaves its token-verified workspace and child source. Protocol 1.11 permits user-reviewed discard only for the narrow verified nested-workspace shape; protocol 1.21 permits copy-only independent reopen of one exact verified source. Extraction disposition and automatic recursive orphan deletion remain closed.
- Nested-workspace recovery is local, path-free, and never automatic. Listing offers only candidates that an exclusive no-follow inspection proves are inactive and exactly shaped; inspection returns an opaque 256-bit ID, source count, aggregate bytes, timestamp, and metadata revision but no temporary path. A disposable tree must have stable nonzero identities, exact-case names, an exact owner record or the empty ownerless post-cleanup shape, ordinary non-reparse one-link files/directories, no named streams, at most 16 source files, no source above 256 MiB, and no aggregate above 512 MiB. Discard repeats the exact revision/count/bytes, reopens the temporary root and every descendant relative to pinned handles, and revalidates the entire shape immediately before the first deletion. Cancellation is honored before that point and deferred afterward through the bounded leaf-to-root sequence. Any changed, additional, hard-linked, streamed, reparsed, identity-unavailable, active, inaccessible, or partially deleted state is preserved. A real authenticated Worker crash test kills the exact PID after the first source deletion; the client reports `worker.disconnected`, and the next ordinary Worker classifies the smaller tree as suspicious without deleting it. Independent reopen additionally repeats the exact selected source ID/length, validates fresh content evidence, and makes a separate depth-zero copy/session while leaving the recovery tree unchanged. An exact-PID post-copy-flush kill proves unchanged original hash/evidence and path-free restart preservation. The metadata revision detects accidental/racy replacement but is not authentication against a malicious process running as the same user.
- Every current ZIP creation now durably writes a local fixed-drive journal before destination staging. Five append-only, SHA-256-checked full-state frames bind `Admitted`, `Writing`, `Finalized`, `CommitIntent`, and `Committed` to the operation ID, canonical destination, destination-parent identity, token-derived staging name, staging identity, and finalized length. The journal contains no source paths, source bytes, passwords, or command-line secrets. It is integrity evidence against torn or accidental corruption, not authentication against a malicious same-user process. Protocol 1.9 can explicitly reopen and revalidate recorded artifacts for review; protocol 1.10 may act only through the separately negotiated, exact-revision, explicit disposition request. Neither mechanism is automatic retry authority.
- ZIP creation retains two small hard-kill residue windows plus post-commit ambiguity, but they are now durably bracketed: termination after native file creation but before deletion disposition may leave the journal-bound sibling while the last complete phase is `Admitted`; termination after durable `CommitIntent` and disposition clear but before no-replace rename may leave the identity-bound staging file; termination after rename may leave a complete destination with `CommitIntent` or `Committed` but no client terminal. Preparing a unanimous-zone ADS adds one bounded stream-create/identity-check step to the first window; no archive or provenance payload is written there. Exact-process tests prove that a kill during a real 128 MiB Maximum-compression copy with a prepared provenance stream and a kill after writer finalization/durable flush while a 4,096-entry source-tree manifest is being revalidated publish no destination and leave no delete-pending staging file after process exit. The copy-kill preserves a valid `Writing` record, and a second worker reports it without contacting the destination, disclosing paths, or deleting anything. Protocol 1.9 tests cover explicit exact/missing/replaced/length-mismatched/wrong-kind/hard-linked/multiple/torn evidence and prove inspection preserves artifact bytes. Protocol 1.10 tests cover all four disposition actions, stale-revision and hard-link refusal before mutation, durable-intent conflict refusal, same-action replay after the destination path becomes unavailable, torn first-receipt restart, corrupt-receipt preservation, parent-rename exclusion, and deterministic interruption after intent and after artifact mutation. Two additional tests start a non-shipping wrapper around the production `WorkerProgram`, complete the authenticated `ArchiveClient` named-pipe handshake, issue the real disposition request through `WorkerHost`, wait for the exact durable-intent or post-rename checkpoint, and externally kill only that authenticated Worker PID. The client reports a disconnected worker; a fresh ordinary Worker then verifies the pre/post-commit disk state and completes or reconciles once without duplicate publication, followed by path-independent replay. The wrapper contributes only a synchronous checkpoint callback and is never shipped. Cancellation against a genuinely blocked UNC destination remains unverified. Ordinary cancellation/failure removes exact staging and journal state; only explicit reviewed disposition may reconcile retained creation state.
- Disposition receipts contain one durably flushed `Intent` frame before mutation and one `Completed` frame only after the required postcondition. A same-action replay returns the stored result; a different action against a durable intent is refused. Completed receipts are omitted from the attention inventory and retained only as a bounded replay cache: the newest 256 remain eligible for at most 30 days, with one count-prune attempt after each new resolution and at most 256 exact metadata-tree deletions during startup. Count pruning requires complete bounded enumeration; a truncated scan cannot use rank as deletion authority. Every age/count deletion reparses, exclusively reopens, identity-checks, and immediately revalidates the exact ordinary two-file metadata tree without contacting the archived destination. A pruned replay returns path-free `recovery.not_found`. Receipts protect against torn or accidental corruption, not a malicious process under the same user account.
- Preview-cache directory checks are path-based rather than handle-relative and do not transactionally seal the directory against a hostile same-user replacement between validation and file creation. Random `CreateNew` names prevent overwriting an existing object, `FileShare.None` rejects ordinary second readers/writers while the live decrypted file exists, and delete-on-close bounds ordinary residue. This is still not a complete same-user confidentiality boundary: another process under that account can enumerate the name and may inspect Rain's memory or handles when granted debugging/equivalent rights. The current cache deliberately exposes no filesystem path through its API and must not be passed to Shell preview handlers or executed. A separately reviewed private-directory/ACL or brokered-handle design, path lease, and download-provenance policy are required before external path-based preview is enabled or stronger same-user isolation is claimed.
- Filesystems or network servers that do not honor Windows share and file-identity semantics weaken source leases and commit assumptions. Read operations still perform fingerprint checks, but the fingerprint is not a full-file cryptographic hash. Physical CachyOS/Samba 4.24.6 extraction evidence covers remote source/destination success and a disconnect after real progress: success hash-matched all files, while interruption failed authoritatively without a final destination and retained one attributable remote staging tree that could not be removed while the server was unreachable. This does not qualify every SMB implementation or the writer. The new ZIP writer has local automated and loopback-UNC source/destination coverage; an actual second-machine SMB source/destination/interruption creation matrix remains unverified.
- Source-directory overlap and destination-inside-tree admission currently compare canonical path strings plus exact root identities; they do not prove equivalence across every 8.3 alias, mapped-drive, DFS, or alternate UNC spelling. A missed alias is expected to fail later through locked source handles, staging visibility, resource limits, or final manifest revalidation, but that is defense in depth rather than a proven alias classifier. `FILE_ID_BOTH_DIR_INFO` child IDs are compared with the reopened handle when Windows reports a nonzero file ID. Filesystems that report no usable child ID fall back to the reopened-handle snapshot and final manifest comparison, weakening only the enumeration-to-open binding. Alias and no-file-ID filesystems remain explicit compatibility/adversarial gates.
- Handle-relative creation and commit prevent path lookup swaps from redirecting the operation, and manifest/identity/link-count checks detect mutations visible during validation. They do not transactionally freeze directory contents. Creation source snapshots bind identity, length, and timestamp while ordinary write/delete opens are denied, but they are not a full-content cryptographic proof: a hostile pre-existing writable mapping could alter same-length bytes and restore metadata without detection. A malicious process running as the same user can also discover extraction-tree or archive-file staging and may add, modify, or hard-link content after the final check but before or after rename; Windows directory sharing modes do not seal child creation, and directory oplocks are advisory for content changes. The current ordinary-failure extraction cleanup has a same-user time-of-check/time-of-use window after its identity/no-reparse scan. Full-source hashing or a broker running as a different principal, private ACL design, and fully handle-relative cleanup remain decision gates if hostile same-user processes enter the release threat model.
- Expansion ratio currently uses provider-reported compressed sizes because the managed API does not expose measured compressed-byte consumption. The independent decoded-byte ceiling and disk reserve are authoritative; ratio is defense in depth until a measured-input provider seam exists.
- The managed provider's synchronous archive-construction call cannot be interrupted inside SharpCompress. Cancellation is checked before and immediately after that call and throughout Rain-owned metadata validation/indexing. Sequential readers retain one forward reader for ascending copies, reset on backward access/error/cancellation, and enforce a 64 GiB aggregate decoded-work ceiling, but the first integrity/extraction copy of a compressed TAR intentionally pays one additional full outer-stream validation pass. The client can terminate only its authenticated owned Worker after bounded cancellation/close settlement. This contains the owned process but does not make provider parsing cooperatively cancellable or prove physical blocked-network latency.
- Multipart classification combines provider volume enumeration with bounded known format signals; it is not a proof that every unrecognized provider-accepted layout is single-volume. ZIPs without a valid terminal EOCD, or with ZIP64 sentinel fields but no locator, are rejected during open as `archive.invalid_zip_central_directory`; they are not exposed as list-only sessions. Additional ZIP/7z/RAR naming and layout variants remain an M2 conformance gate. Before broader multipart support, the provider contract must distinguish confirmed single-volume, confirmed multipart, and unknown and expose the complete volume set for identity locking. The ZIP tail classifier reads at most 65,633 bytes, but that file open/read is synchronous and may still stall on a hostile network filesystem; worker teardown is the current outer bound.
- The normal client cannot exceed eight simultaneous control requests. A malformed authenticated peer that sends a ninth while all permits are held causes the worker connection to fail closed rather than receiving a structured resource-limit response; a friendlier overload response is a later hardening decision.
- The response-written/start-task ownership rule is covered on each side of the boundary, but a dedicated fixture that makes a successful start response physically written and deliberately unread while client fallback begins remains lower-priority race coverage.
- Current creation is unencrypted, single-output, and new-destination-only. ZIP, TAR-family, and conditionally RAR routes support bounded explicit/tree input; raw GZIP/BZIP2 accept exactly one file. None overwrites or updates an archive or creates split volumes. RAR creation is enabled only when the Worker verifies the ordinary x64 `C:\Program Files\WinRAR\Rar.exe` as Authenticode-trusted `win.rar GmbH`, version 7.23 through 7.x. The encoder is user-installed and separately licensed; Rain neither bundles it nor searches `PATH`, current directory, or registry. Only the concrete Worker-owned WinRAR provider may grant authority; capability query, request admission, and post-queue execution each re-resolve it. The provider revalidates the executable and holds it without write/delete sharing through every native invocation. Installation after Worker startup is `RestartRequired`; missing, old, removed, replaced, untrusted, or unsupported encoders advertise a typed closed capability. The Worker materializes only validated stream content in a random token-owned private workspace, invokes the encoder without a shell, requires zero exit plus independent archive test and exact SharpCompress manifest/digest readback, then copies into Rain's existing guarded staged/no-replace transaction. A live workspace holds an exclusive durable owner claim. Post-handshake maintenance runs outside request dispatch under one global 1,024-candidate/16,384-object/two-second budget; stable root ancestry, candidates, and owner records are opened no-follow and must be ordinary non-reparse one-link objects. It deletes only an inactive exact-name/exact-record tree from one complete bounded inventory; active, suspicious, unreadable, changed, or over-limit state is preserved with one fixed warning. Cancellation must prove the exact encoder child exited after kill, and an unproven kill tears down the Worker connection instead of emitting a false terminal. Cleanup failure is propagated after owned handles are released. Exact-PID proof covers live preservation, hard-kill residue, next-process cleanup, and unrelated-sibling preservation. This is crash cleanup under the declared same-user model, not a hostile same-user filesystem sandbox. ZIP encryption has no approved writer, SharpCompress XZ compression is unavailable, and 7z creation remains behind the rejected native adapter/package gate. Any future split output requires a durable multi-output manifest/journal and partial-publication recovery contract; any replacement route requires separately approved typed conflict/backup/recovery semantics. The current route never mutates an original and preserves an existing or raced destination, so rollback is intentionally unnecessary. Hash-verified official-7-Zip, Windows-libarchive, GNU, WinRAR, distinct libarchive-3.8.9, and Rain round-trip proofs cover the qualified simple/PAX corpora, retained automated package, and retained local performance probes. The exact staged PAX timestamp is preserved; SharpCompress's public descriptor may differ by one 100 ns tick for fractional values, which is retained as a read-metadata limitation rather than used for publication authority. BCL-generated `./PaxHeaders.<process-id>/` helper names disclose the ephemeral Worker PID and prevent byte-reproducible PAX containers across processes; Rain's qualified determinism is the planned material namespace/order/content/metadata, not container bytes. Exact-package non-elevated ACL denial, early and near-final true NTFS exhaustion, all supported preset families on exFAT, fresh offline Sandbox, and local 8.3/mapped-drive/alternate-loopback-UNC paths pass. Product-owner direct ZIP creation/reopen/integrity and Rebuild Copy observation now passes; the submitted placeholder staging query proves no cleanup state. Actual SMB provenance/interruption, blocked-UNC cancellation, DFS/no-file-ID behavior, current RAR child-process containment on a machine with qualifying WinRAR installed, Recovery Center, product-owner accessibility, and release acceptance remain gates rather than claimed coverage. Open-ended version/method/layout breadth remains Milestone 8 release hardening.

The detailed invariants and remaining gates are recorded in `docs/architecture.md` and `docs/milestone-1.md`.

## Reporting a vulnerability

Do not attach a live malicious archive to a public issue. Provide a minimal description, affected version, and a private way to obtain the fixture. Preserve the original archive hash and generating steps where possible.

Passwords, private filenames, entry contents, and filesystem paths should be removed from reports unless they are essential to reproduce the problem.
